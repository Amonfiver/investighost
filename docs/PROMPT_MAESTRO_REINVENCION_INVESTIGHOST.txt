====================================================================
1. CONTEXTO GENERAL DEL PRODUCTO
====================================================================

Investighost es el centro privado de operaciones de Trawel.

Trawel es el escaparate público:
- abre su base de datos,
- obtiene contenido publicado,
- muestra países, ciudades, destinos, experiencias y anuncios,
- permite navegar, descubrir y consultar.

Investighost es la fábrica, oficina y panel de control:
- investiga destinos,
- contrasta fuentes,
- genera contenido,
- permite editar y revisar,
- almacena producción,
- administra cola editorial,
- publica en la base que Trawel ya sabe leer,
- modera aportaciones y fotografías de usuarios,
- gestiona clientes y anunciantes,
- organiza campañas,
- controla anuncios y fechas de caducidad,
- analiza estadísticas,
- genera informes comerciales,
- envía comunicaciones permitidas,
- mantiene trazabilidad completa.

Investighost debe ser fácil de usar por personas no técnicas.

Flujo básico de contenido:
1. Escribir destino.
2. Elegir proveedor o estrategia de IA.
3. Investigar.
4. Esperar resultado.
5. Revisar.
6. Corregir fácilmente.
7. Guardar en la base interna.
8. Aprobar.
9. Añadir a cola.
10. Publicar en Trawel cuando corresponda.

La producción interna y la publicación externa deben permanecer separadas.

Ejemplo:
- hoy pueden producirse 30 piezas,
- pero publicarse 3 o 5 por día,
- manteniendo una salida constante y controlada.

4. DECISIÓN TECNOLÓGICA CANÓNICA
====================================================================

Mantener TypeScript como lenguaje principal.

STACK PRINCIPAL
---------------
Aplicación de escritorio:
- Electron
- React
- TypeScript
- Vite

Contratos y validación:
- TypeScript
- Zod

Persistencia local:
- SQLite
- Drizzle ORM

Persistencia cloud y operaciones compartidas:
- Supabase Postgres
- Supabase Auth
- Row Level Security
- Supabase Storage
- Supabase Edge Functions
- Supabase Cron cuando haya tareas que deban ejecutarse aunque la aplicación esté cerrada

Correo:
- arquitectura desacoplada por proveedor,
- primer candidato: Resend,
- correo transaccional para mensajes individuales o avisos,
- Broadcasts/segmentos para campañas de marketing,
- webhooks para entregas, aperturas, rebotes, bajas y respuestas cuando el proveedor lo permita.

Investigación web:
- proveedores de IA con búsqueda web, inicialmente Kimi y OpenAI,
- arquitectura multi-proveedor,
- Playwright únicamente cuando sea necesario automatizar una web que no disponga de API adecuada y siempre respetando términos, robots, límites y legalidad.

NO introducir Python, Java u otro runtime principal en el MVP salvo que una necesidad concreta y demostrada no pueda resolverse razonablemente con TypeScript.

Motivo:
- el proyecto ya está construido en TypeScript,
- se evita mantener dos ecosistemas,
- Electron, Node, Supabase, Drizzle, Zod, Resend y Playwright funcionan bien con TypeScript,
- facilita a Cline/Codex mantener contratos consistentes.

Python podrá evaluarse en el futuro para trabajos especializados de análisis de datos o ML, pero no como dependencia base del producto.

5. ARQUITECTURA HÍBRIDA OBLIGATORIA
====================================================================

Investighost no debe depender completamente de que el PC esté encendido.

DIVISIÓN DE RESPONSABILIDADES
-----------------------------

Aplicación Electron:
- interfaz de trabajo,
- edición,
- revisión,
- configuración,
- paneles,
- operación manual,
- caché local,
- trabajo offline parcial,
- acceso seguro mediante preload e IPC.

SQLite local:
- borradores locales,
- caché,
- historial de trabajo local,
- colas temporales,
- datos que no necesitan sincronización inmediata.

Supabase:
- datos compartidos entre operadores,
- usuarios y roles,
- cola editorial compartida,
- moderación,
- CRM,
- anuncios,
- campañas,
- analytics,
- auditoría,
- sincronización,
- configuración central.

Edge Functions:
- operaciones privilegiadas,
- publicación en Trawel,
- envío de correos,
- recepción de webhooks,
- acceso a secretos,
- tareas server-side.

Supabase Cron:
- publicaciones programadas,
- recordatorios de caducidad,
- comprobaciones de campañas,
- digest e informes,
- tareas recurrentes.

REGLA DE SEGURIDAD
------------------
- Nunca exponer service-role keys en renderer.
- Nunca guardar secretos en SQLite sin cifrado.
- Renderer sin nodeIntegration.
- contextIsolation activo.
- IPC limitado y tipado.
- Operaciones privilegiadas por Edge Functions o proceso principal seguro.
- Usuarios remotos deben usar Supabase Auth y RLS, no una clave administrativa compartida.

6. ROLES DE USUARIO PREVISTOS
====================================================================

Diseñar como mínimo estos roles, aunque su implementación se haga por fases:

owner
- control total,
- configuración,
- claves,
- usuarios,
- permisos,
- publicación final,
- informes completos.

admin
- gestión operativa amplia sin acceso indiscriminado a secretos.

editor
- generar, editar, guardar y preparar contenido.

reviewer
- revisar, corregir, aprobar o rechazar.

publisher
- gestionar cola y publicar contenido aprobado.

moderator
- revisar aportaciones, reportes y fotografías de usuarios.

sales
- gestionar clientes, oportunidades, campañas y anuncios.

analyst
- consultar estadísticas e informes sin modificar contenido.

Una persona puede tener varios roles.

La UX para editor/reviewer debe ser especialmente sencilla para una persona sin conocimientos técnicos.

====================================================================
10. REGLAS DE EJECUCIÓN POR FASE
====================================================================

Antes de cada fase:
1. Releer docs relevantes.
2. Revisar git status.
3. Proponer checkpoint.
4. Declarar alcance.
5. Listar archivos previstos.
6. Identificar riesgos.
7. Confirmar dependencias.

Durante:
- cambios pequeños,
- código tipado,
- sin dependencias innecesarias,
- sin reescribir todo,
- sin lógica ficticia oculta,
- sin mocks presentados como reales.

Después:
1. lint,
2. typecheck,
3. tests,
4. build,
5. prueba funcional,
6. revisar git diff,
7. actualizar BITACORA,
8. actualizar docs si cambió una decisión,
9. entregar resumen,
10. proponer commit en español.

Formato del commit:
- feat:
- fix:
- docs:
- refactor:
- test:
- chore:
- checkpoint:

No hacer push automático salvo autorización expresa.

====================================================================
11. REGLA DE PAUSA Y RECUPERACIÓN
====================================================================

Si algo falla:

1. No encadenes parches.
2. Identifica causa raíz.
3. Explica:
   - síntoma,
   - causa,
   - archivos implicados,
   - riesgo,
   - solución propuesta.
4. Decide si corresponde:
   - Cline para implementación,
   - Codex para auditoría/revisión/corrección.
5. Crea checkpoint antes de corregir.
6. Corrige un bloque pequeño.
7. Verifica.
8. Continúa desde el mismo punto de la hoja de ruta.

Nunca reinicies la hoja de ruta desde cero por un fallo local.

====================================================================
12. CRITERIOS GLOBALES DE CALIDAD
====================================================================

El sistema debe ser:
- comprensible,
- seguro,
- mantenible,
- modular,
- trazable,
- usable por no técnicos,
- preparado para delegación,
- orientado a datos reales,
- honesto con incertidumbre,
- compatible con Trawel,
- escalable sin sobreingeniería.

No se acepta:
- secreto en renderer,
- key en Git,
- email sin trazabilidad,
- publicación sin revisión,
- fuente inventada,
- métrica inventada,
- anuncio vencido activo,
- foto sin derechos claros,
- campaña sin bajas,
- estado ambiguo,
- escritura destructiva sin confirmación,
- automatización que dependa de tener abierto Electron.
